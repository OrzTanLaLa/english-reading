# 鸿蒙版：拍照课文 → 大模型 TTS 朗读 → 语音提问的 Agent 生词本

> 版本 v4（TTS 全部改为云端大模型语音合成）｜2026-10-20  
> 平台：HarmonyOS，主力设备 MatePad 横屏；开发机 Windows + DevEco Studio  
> 交付物：一个自用 HAP，数据落在本机，生词写到 `filesDir/vocab.txt`

## 0. 结论先行

### 0.1 TTS：全云，选大模型语音合成

放弃端侧 `textToSpeech`，理由不只是音质：

| | 端侧 `@kit.CoreSpeechKit` | 云端大模型 TTS |
|---|---|---|
| 英文音色 | 只有 Laura 一个，需 5.1.1+ 手动下载 | 多音色可选，自然度高一个档 |
| **词级时间戳** | **没有**（只有 onStart/onComplete） | **有**（字级 begin/end time） |
| 韵律与停顿 | 固定，长文听感疲劳 | 可调语速/语调；**SSML 实测无效**（见 §3.4.9） |
| 成本 | 免费 | ≈ ¥2/万字符 |
| 离线 | 支持 | 不支持 |

逐词高亮是「跟读」体验的核心，端侧拿不到时间戳，这一条就足以否掉它。

### 0.2 推荐组合

| 角色 | 选型 | 说明 |
|---|---|---|
| **主 TTS** | **阿里云 CosyVoice-V2**（百炼） | 已核实：字级时间戳、WebSocket 流式、PCM/WAV/MP3/OPUS、¥2/万字符、RPM 180 |
| 备 TTS | 火山引擎「豆包语音合成大模型」 | 英文音色更自然；时间戳字段需实测确认 |
| 试听对比 | MiniMax Speech-02 / 讯飞星火 TTS | 只在选音色阶段用 |

两家走同一个 `TtsProvider` 接口，换供应商只改一个文件。**先用 CosyVoice 打通**（能力确定），再拿豆包对比听感，喜欢哪个用哪个。

### 0.3 合成粒度：按语义单元，≤300 字符

300 是**普通语音合成接口的截断线**（「超过 300 个字符的内容将会截断」），超过就丢内容——所以每次请求必须压在这条线以下。CosyVoice 单次上限 2 万字符，实测 446 字符未截断，但按 300 走更稳，缓存和编辑粒度也合适。

事件流里的 `sentence-begin` 只是分句标记，不代表音频被切开重造——**一次请求内的音频是连续生成的**。真正的接缝只在跨请求边界，所以：

- 用 LLM 把课文切成「语义完整 + ≤300 字符」的单元，一次请求一个字单元；
- 一篇文章 6–10 次请求，也就 6–10 个真接缝；
- 组间静音可调（300–600ms），按精听/泛读切换。

音质好坏由使用者判断，这里只固定结构。

## 2. 主链路

### 2.1 导入

```
Core Vision Kit 文档扫描（多页，自动裁边）
  → textRecognition 端侧 OCR（带 bbox）
  → 段落重建（分栏 / 行距 / 页眉页脚 / 中文注释过滤）
  → [可选] 云端 VLM 复核可疑页
  → 校对页 → 分句入库
```

### 2.2 朗读

```
句组文本（整句攒到 ≤300 字符，已规范化标点） → 查缓存（命中直接播）
  → 未命中：WebSocket 合成该组，边收 PCM 边写入 AudioRenderer
  → 时间戳入库：subtitles[{text, begin_index, end_index, begin_time, end_time}]
  → 对齐到原文 token → 播放时按时间高亮到词
  → 组末插入 400–450ms 静音，接下一组；播到 30% 时后台预合成下一组
```

### 2.3 语音提问

```
长按麦克风（≤15s）→ PCM → 打包 WAV
  → Qwen3-Omni（CQR）：课文 + 音频 → {sentence_id, span, intent, question, confidence}
  → 本地校验 span → 从原文截 surface（拼写一定正确）
  → 主 Agent（文本 + 工具）→ 流式回答
  → 判定要记 → append_vocabulary → 写 txt
```

### 2.4 落盘

```
Agent 调 append_vocabulary → JSON 校验 → 幂等检查 → 单写者追加 → fsync
```

### 2.5 分层：哪部分能跨平台复用

判断标准只有一条：**输入输出都是 string / JSON、不碰 IO 的，就能复用。**

| 层 | 内容 | 平台依赖 | 移植成本 |
|---|---|---|---|
| **core** | 标点规范化、分句、分组校验、时间戳对齐、JSON 契约、提示词、生词本格式 | 无 | **0** |
| **agent** | 工具调用循环、工具实现、system prompt | 只依赖 adapters 接口 | 换 10 处调用 |
| **adapters** | 网络（http/SSE/WS）、文件、音频、OCR、密钥 | 全部 | 全部重写 |
| **ui** | ArkUI 页面 | 全部 | 全部重写 |

粗略量级：core 约 1500 行、agent 约 400 行、adapters 约 600 行、ui 约 3000 行。**移植省下的是「业务规则」，不是「代码量」**——但业务规则恰恰是最难重新想一遍的部分。

```
app/src/main/ets/
  core/          ← 纯 TS，零平台依赖，可在 Node 里跑单测
    normalize.ts     标点规则（破折号→逗号、分号→句号、全角→半角）
    segment.ts       分句 + 30 条缩写保护
    plan.ts          语义分组计划的校验与修长
    align.ts         词级时间戳 → 原文 token（LCS + 词边界吸附）
    contracts.ts     Tool / Plan / CQR 的 interface 与 Schema
    prompts.ts       分组、CQR、Agent 三个 system prompt
    vocab.ts         块式文本的生成与解析
  adapters/      ← 每个平台各写一份，接口固定
    net.ts / storage.ts / audio.ts / ocr.ts / secure.ts
  agent/         ← 只依赖 core + adapters 接口
    loop.ts / tools/*.ts
  ui/            ← ArkUI
```

**为什么 core 用 TypeScript**：ArkTS 是 TS 的严格子集，core 写完能直接在 Node 里跑测试；将来若移植到 Web / React Native 也能直接用。如果移植成 Swift / Kotlin 原生，core 要重写——但规则、边界条件、测试用例都留下来了，重写是有依据的。

**黄金测试**：Python 版已经产出 fixture（t1/t2/t3 的分句结果、分组计划、词级对齐）。TS 版 core 必须逐字符一致，否则移植时会出现「看起来一样、边界差一个字符」的隐性 bug。

> 不必为了移植性牺牲当前实现。现在只做鸿蒙，core 用 TS 已经足够。

## 3. 模块详设

### 3.1 扫描与 OCR

- **扫描**：Core Vision Kit 文档扫描（自动检测边缘 → 透视矫正 → 整页图），多页管理自己写。
- **OCR**：`textRecognition.recognizeText()` 端侧，返回文本块 + bbox + 置信度。
- **段落重建**（鸿蒙需自写）：
  1. 按 y 中心聚行，行内按 x 排序；
  2. 一行中部空隙 >8% 页宽 → 判双栏，先左后右；
  3. 行距 < 中位 1.4 倍 → 同段；字号差异 >30% → 标题/注释；
  4. 上下 8% 区域且多页重复 → 页眉页脚，丢弃；
  5. 行尾 `-` + 下行小写开头 → 拼接断词；
  6. 中文字符占比 >30% 的行标 `note`，不进朗读队列。

- **英文 OCR 是鸿蒙最大的未知数**，需实测。不达标就把主路切云端 VLM（Qwen-VL-Max / GLM-4V），约 ¥0.01/页。

### 3.2 校对页

必须有。低置信度行高亮 + 可编辑全文 + 原图对照 + 「朗读范围」勾选。改完按句 diff，只失效受影响段落的音频缓存。

### 3.3 分句与高亮

- 分句：`[.!?]` + 空白 + 首字母大写为主规则，配套缩写例外表（`Mr.` `Dr.` `e.g.` `i.e.` `U.S.`）、引号内句号、省略号、对话破折号；允许长按合并/拆分。
- 分词：按空格与 `'` `-` 切，保留字符偏移。
- **高亮**：`subtitles` 给的是字符区间 + 毫秒区间，先用 `begin_index/end_index` 把词映射到字符位置，再用 `begin_time/end_time` 驱动动画。每个词一个时间片，二分查找即可。
- **必须做一层对齐**：TTS 返回的 `words` 不能直接拿去高亮，实测有四种脏数据——带前导空格（`' not'`）、连字符被归一（`long-term` → `longterm`）、标点并入相邻词（`.A`）、首词时长为 0。做法：normalize 后用 `difflib` 对回原文 token，命中的继承时间，未命中的在左右已知时间之间线性插值。否则高亮会在屏幕上「跳词」——TTS 的切词和你的分词本来就不一致。

### 3.4 云端大模型 TTS（核心）

#### 3.4.0 音色策略：四选一，不选冠军

B0-a 实测结论：**CosyVoice 的四个英文音色（温柔女声 / 睿智旁白 / 青年男声 / 老年男声）都可接受**，主观上难分高下。与其替用户选，不如做成设置项。

| 音色 ID | 展示名 | 定位 | 所属模型 | 默认 |
|---|---|---|---|---|
| `longbaizhi` | 睿智旁白（女） | 叙述中性、不易疲劳 | cosyvoice-v2 | **✅ 默认** |
| `longwanjun` | 温柔女声 | 亲切，适合轻松课文 | cosyvoice-v2 | |
| `longanyang` | 青年男声 | 明快，适合说明文 | **cosyvoice-v3-flash** | |
| `longlaobo` | 老年男声 | 沉稳，适合故事/传记 | cosyvoice-v2 | |

**音色与模型是绑定的**：`longanyang` 在 v2 上会直接报错，必须走 v3-flash。App 里做成 `{voice → model}` 的映射表，别让用户碰。

实测首包延迟（2026-10-20，每次新建连接）：v2 音色 **1.67–2.13s**，v3-flash **0.66–0.73s**，差 2.5 倍。首包含 WebSocket 握手，App 内复用连接后还能再降。这意味着 **M1 必须做流式播放**，不能等整段合成完再播。

默认选 `longbaizhi` 的理由很简单：课文朗读以叙述为主，旁白型女声最中性，长时间听最不容易烦。**这不是数据结论，只是一个合理的起点**——反正用户能换。

三条工程约束：

1. **缓存键必须含 `voice`**（已经在 §3.4.5 里）。切换音色 = 该文章音频全部失效，首次播放需重合成，约 ¥0.6/篇。UI 上要提示一句「切换音色后，本文需重新生成语音」，否则用户会以为卡住了。
2. **设置页要有试听**：合成一句固定短句（如 "This is how I will read your text."），约 15 字符，成本可忽略，按音色缓存。
3. **只暴露展示名，不暴露音色 ID**。用户不需要知道什么叫 `longbaizhi`，那是我们的事。

#### 3.4.1 选型对比

| 服务 | 字级时间戳 | 流式 | 英文听感 | 价格 | 备注 |
|---|---|---|---|---|---|
| **阿里云 CosyVoice-V2** | ✅ `enable_subtitle` | ✅ WebSocket | 好 | **¥2/万字符**（北京） | 能力和价格都确认过，**首选** |
| 火山 豆包语音合成大模型 | 需实测 | ✅ | **最好** | 需查（同量级） | 英文音色最自然 |
| MiniMax Speech-02 | 需实测 | ✅ | 很好 | 略高 | 音色年轻化 |
| 讯飞星火 TTS | 部分支持 | ✅ | 好 | 中等 | 中英混读稳 |
| 阶跃 Step-TTS | 需实测 | ✅ | 好 | 低 | 新，生态较薄 |

CosyVoice-V2 已确认的细节（据[官方接口文档](https://help.aliyun.com/zh/isi/user-guide/siso-text-to-speech-synthesis-for-cosyvoice-interface-description.md)）：

- `enable_subtitle=true` + 选支持时间戳的音色 → `SentenceSynthesis` / `SentenceEnd` 事件返回 `subtitles[]`；
- 每条字幕：`text`、`begin_index`、`end_index`、`begin_time`、`end_time`（毫秒）；
- 音频格式 `pcm / wav / mp3 / opus`，采样率 8k/16k/24k/48k，默认 16k PCM；
- `speech_rate` -500~500、`pitch_rate` -500~500、`volume` 0~100；
- ~~`enable_ssml=true` 时可用 SSML~~ —— **实测无效**：传 SSML 标签会被当普通文本**念出来**（`<break time="500ms"/>` 直接朗读），不要用；
- 单会话单次 ≤1 万字符，累计 ≤20 万字符。

> 计费口径注意：**英文字母、标点各计 1 字符，汉字计 2 字符**。所以英文课文的计费基本等于字母数。

#### 3.4.2 合成粒度：按语义单元，控制在 300 字符左右

**先澄清一个被我搞混的概念。**

官方对「300 字符」的定义是截断阈值：「支持一次性合成 300 字符以内的文字……超过 300 个字符的内容将会截断」——这是**普通语音合成**接口的规则。CosyVoice 单次上限是 2 万字符，实测 446 字符的请求完整输出（chunk 文本合计 446 字符，末尾 `open question.` 未丢）。

而事件流里的 `sentence-begin` **是分句标记，不是「音频被切成独立生成的块」**。同一次请求内的音频是连续生成的，模型全程握着完整文本。所以我此前把「事件数 > 1」等同于「声学接缝」，这个推断是错的。

**真正的接缝只存在于跨请求边界。** 一次请求内部怎么分句是引擎的事，内容不丢、上下文不断。

由此得出：

| 结论 | 说明 |
|---|---|
| 请求越少，真接缝越少 | 一篇文章切 6–10 次 vs 40 次，差别在这里 |
| 切分依据是**语义**，不是字数 | LLM 把课文切成「语义完整、≤300 字符」的单元，是最优解 |
| 300 是安全上界，不是魔法数字 | 受接口截断线约束；同时兼顾缓存粒度与编辑粒度 |

**三种粒度实测**（t2 全文，445 字符，`segment_probe.py`）：

| 方案 | 请求数 | 时长 |
|---|---|---|
| A 整段一次 | 1 | 25.3s |
| B 逐句 | 5 | 27.2s |
| **C 整句攒组（≤300 字符）** | **2** | **26.2s** |

三个版本时长差异主要来自插入的静音（B 插了 4 段 450ms），**不构成音质优劣的证据**——音质由人判断。

采用 C 的理由是工程性的：凑够 300 字符减少请求数，同时不超过截断线，缓存粒度也合适。

| | A 整段 | B 逐句 | **C 攒组（采用）** |
|---|---|---|---|
| 真接缝数 | 0 | 40 | 6–10 |
| 单次是否可能超截断线 | 是（>300 时） | 否 | 否 |
| 缓存失效粒度 | 整段 | 一句 | 一组 |
| 逐句跳转 | 时间戳换算 | 天然 | 时间戳换算 |

代价和对策：

- **组边界有接缝**：一篇文章 6–10 处。静音时长可调（精听 600ms，泛读 300ms）；若听感不行，再用「重叠合成」补（合成是确定性的，裁掉的部分与已播音频逐字节相同，见 §3.4.10）。
- **延迟**：每组一次请求。靠预取——当前组播到 30% 时合成下一组。
- **分句规则**见 `segment.py`：`(?<=[.!?])\s+(?=[A-Z"“(])` 加 30 条缩写保护。**必须先规范化标点再分句**——分号会变成句号，句子数会变。

#### 3.4.2.1 交给 LLM 做语义切分

规则分句只能保证「切在句号后」，保证不了「切在语义闭合处」。用主 Agent 的同一个模型做一步离线切分：

```json
{"units": [[0,1], [2], [3,4]], "gap_after_ms": [300, 800, 450]}
```

- 模型只输出**句子索引分组**，不输出字符数——它数不准，也不该数；
- 长度约束由代码强制：贪心累加，超 300 就断组；单句本身超 300 时在子句边界再切；
- `gap_after_ms` 给出每组的停顿长度，消掉统一 450ms 的机械感；
- 成本 ¥0.01/篇，在导入阶段后台跑，不影响首句延迟。

**实测（DeepSeek-chat，2026-10-20）**：三篇课文的重试 0 次、回退 0 次，分组结果与人工判断完全一致——包括 t2 的对比两句没被拆、t1 的结尾短句独立成拍。t3 被模型塞成一组（324 字符），代码自动切成 230 + 94 两组，`gap_after_ms` 由代码补 200ms。

> 代码补的停顿（200ms）比模型给的值保守。如果听感偏急，把这个默认调到 300–350ms。

#### 3.4.3 合成与时间戳入库

```ts
// 伪代码：一次段落合成
const session = await cosy.startSynthesis({
  voice: 'longxiaochun_v2',        // 需选「支持英文 + 支持时间戳」的音色
  format: 'pcm', sampleRate: 16000,
  speechRate: 0, enableSubtitle: true
});
for await (const ev of session.send(paragraphText)) {
  if (ev.audio)        renderer.write(ev.audio);        // 边收边播
  if (ev.subtitles)    subtitles.push(...ev.subtitles); // 累积
}
// 落库
paragraph.audioKey = sha256(text + voice + rate);
paragraph.subtitles = subtitles;   // 字级时间戳
paragraph.sentenceStarts = 由 subtitles 的字符索引反查每句起始 begin_time;
```

**关键**：`begin_index/end_index` 是相对整段文本的字符下标，正好能和你的分句结果对齐——不需要再做任何对齐算法。

#### 3.4.4 播放

- 用 `AudioRenderer` 直接写 PCM（16k/16bit/mono），采样率与 TTS 输出一致，免转码；
- 播放进度 = 已写入帧数 − 缓冲区余量，或直接用 `getAudioTime()`；
- **暂停/继续**：`renderer.pause()` / `start()`，位置天然保留；
- **跳转到某句**：`seek` 到该句 `begin_time` 对应的采样点（PCM 缓存在本地，随机访问很容易）；
- **倍速**：`AudioRenderer.setSpeed()`（0.5–2.0），不需要重新合成；
- **后台播放**：申请长时任务 `KEEP_BACKGROUND_RUNNING` + `BACKGROUND_MODE_AUDIO_PLAYBACK`；
- **锁屏控制**：目前鸿蒙没有 iOS 那样的全局 Now Playing API，用 `AVSession`（媒体会话）接入系统播控中心。

#### 3.4.5 缓存与预取

```
key  = sha256(组文本 + voice + speechRate + pitchRate + format)   # 组 = 攒到 ≤300 字符的整句组合
file = context.cacheDir/tts/<key>.pcm     (16k 16bit mono ≈ 1.9MB/分钟)
meta = <key>.json                          (subtitles + 时长 + 字符数)
```

- 上限 500MB，LRU 淘汰；文章级「离线包」可固定不淘汰；
- 当前组播放进度到 **30%** 时，后台开始合成下一组；用户点「下一句」时把目标组插队；
- 同一组并发请求要加锁，避免重复合成。

#### 3.4.6 点词发音（很实用的小功能）

用户点某个词 → 单独请求 3–5 秒的慢速发音（`speech_rate: -300`），缓存到 `tts/word/<word>.pcm`。

- 比整句重播快得多，也符合「查生词」的即时反馈；
- 词级请求不返回时间戳也无所谓（不需要高亮）。

#### 3.4.7 失败与降级

| 情况 | 处理 |
|---|---|
| 请求超时（>5s） | 重试 1 次 → 切备用供应商 → 仍失败则提示「这段暂时读不了，可先看文字」 |
| 网络断开 | 已缓存段落照常播放；未缓存段落置灰 |
| 字符超限 | 合成前按 1 万字符切块（实际按 600 字符切，不会触发） |
| 返回空音频 | 记录 requestId 便于排查，跳过该段并提示 |
| 音色不支持时间戳 | 启动时校验音色能力；不支持则退化为句级高亮 |

#### 3.4.8 密钥：一个 Key 还是多个

各家不一样，别默认「一个 key 通吃」：

| 平台 | 密钥形态 | 覆盖范围 |
|---|---|---|
| **阿里云百炼**（DashScope） | 一个 API Key（`sk-...`） | **同地域全部模型**：CosyVoice、Qwen3-Omni、Qwen-VL、Qwen 文本 |
| 火山引擎 | 方舟用 API Key；语音合成用 AppID + Access Token | **不通用**，两套控制台分别申请 |
| MiniMax | 一个 API Key + GroupId | 语音与文本通用 |
| DeepSeek | 独立平台独立 Key | 仅文本 |

三个注意点：

1. **Key 绑定地域**：北京和新加坡的 Key 不通用，百炼文档明确写了。
2. **有 Key ≠ 有权限**：还要在控制台「模型广场」开通对应模型，否则报无权限。
3. **计费与限流按模型分别算**，Key 只是一个身份，不是一个套餐。

**本项目实际是两把 Key**：

| Key | 覆盖 | 存哪儿 |
|---|---|---|
| 百炼 `sk-...` | **TTS（CosyVoice）+ CQR（Qwen3-Omni）+ OCR 复核（Qwen-VL）** | App 设置页 |
| DeepSeek Key | **主 Agent**（文本 + 工具调用） | App 设置页 |

两把分开的代价是设置页多一个输入框，好处是主 Agent 不被绑在百炼的模型上——DeepSeek 的 tool calling 和中文解释质量更适合当 Agent。

顺带一个简化：CosyVoice 有两套接入方式——百炼 DashScope（只要 API Key）和智能语音交互 NLS（要 AccessKeyId/Secret 再换 Token）。**选前者**，少一套密钥管理，也少一类泄露面。

**安全**：Key 加密存 `preferences`，不进代码库、不进日志。将来要分享给家人，再加一个极轻的 Token 代理；别把 Key 硬编码进 HAP——反编译门槛极低。

#### 3.4.9 合成前必须做的文本规范化

**合成文本 ≠ 显示文本。** 送给 TTS 的是改写过的标点版本，屏幕上显示的仍是原文。

实测反例（`longbaizhi` + `cosyvoice-v2`）：

> "…which is why so many schools have begun to teach it — though whether a trait like this can be taught at all remains an open question."

破折号让 TTS 把 `though` 判成句末副词：`though` 前停顿 **0 ms**，读成升调，然后从 `whether` 另起一句。改成逗号后，`though` 前出现 129 ms 停顿，整句时长从 11.05s 变成 11.77s——断句结构变了。

规范化规则（按优先级）：

| 原文 | 合成时替换 | 理由 |
|---|---|---|
| `—` `–` `--` | `,` | 破折号是最常见的句法误判源；逗号保留原意且给短停顿 |
| `;` | `.` 或 `,` | 分号同样容易被并句 |
| `(...)` | `, ... ,` | 括号内的内容常被读出奇怪的语调 |
| 全角标点 `，。！？` | 半角 | 英文文本里混入全角会干扰切分 |
| 连续空白 / 换行 | 单个空格 | 换行会被当作强制停顿 |
| 引号 `" "` | 保留 | 不要替换，模型对对话引号处理是对的 |

两条配套设计：

1. **对齐不受影响**：词级对齐是在 normalize 之后按词做的，标点不参与比较，所以改标点不会破坏高亮。
2. **允许覆盖**：有些句子怎么改标点都别扭（比如原文的修辞性破折号）。校对页要支持给某一段单独编辑「朗读稿」，与显示稿分离——这是最后一道兜底，比调 prompt 有效。

**但标点不是停顿控制器。** 实测：破折号改成逗号 vs 改成句号，合成时长 11.88s vs 11.91s，盲听听不出差别，停顿都在 130ms 左右。这个模型对逗号和句号的停顿处理几乎一样，**靠加句号制造长停顿是无效的**。

所以：

| 想要的效果 | 正确做法 | 无效做法 |
|---|---|---|
| 一点点停顿（从句之间） | 换逗号 | — |
| 明显停顿（句与句之间） | **分次合成**，音频之间插 300–500ms 静音 | 加句号 |
| 强调某个词 | 单独合成该词，或整体降速 | SSML `<emphasis>` |
| 任意位置的 break | **不支持** | SSML `<break>` → 会被念出来 |

#### 3.4.10 官方文档里值得记的几条

来自[语音合成 FAQ](https://help.aliyun.com/zh/isi/support/faq-about-speech-synthesis.md)，都是能直接指导实现的：

| 官方说法 | 对我们的意义 |
|---|---|
| **「书名号和破折号暂不支持识别」** | 直接印证破折号必须替换——不是我们猜的，是官方明说 |
| 「冒号和括号作停顿处理」 | 想制造停顿可以用冒号；括号会被读成停顿，所以括号内容要么删要么改逗号 |
| 「普通语音合成支持 300 字符以下的文本」 | 300 是**接口**限制，不是内部切块阈值 |
| 「长文本语音合成最多支持一次合成 10 万字」（异步接口） | 真要做长篇，官方有专门的接口；CosyVoice 走的是普通接口 |
| 「`begin_index`/`end_index` 表示规范化文本单元的索引，不能直接作为原始输入字符串的字符偏移」 | 印证我们必须做 normalize + 对齐，不能拿索引直接切原文 |
| 「语音合成采用概率模型，通用场景读音准确率约 97%」 | 生词读错是常态，别指望调参解决 |
| **音色是中英双语，必须传 `language_hints=["en"]`**（实测） | 不传时 `1990s` 被读成「一千九百九十秒」，`2.4` 读成「二点四」；传了才是 `nineteen nineties` / `two point four` |
| 同一文本、同参数重复合成，输出 **md5 完全一致**（实测） | 缓存 100% 有效；重叠合成裁掉的那段与已播音频逐字节相同，接缝是真正连续的 |

关于「切分规则」，官方**没有**文档化。实测结论：切块数与字数没有稳定的对应关系，83 字符的单句也会被切成两块。所以控制切分不能靠字数。

#### 3.4.11 合成流水线（已验证）

七步，缺一不可。三篇测试文本全部跑通，词级对齐 100% 直接命中。

| # | 步骤 | 实现 | 关键点 |
|---|---|---|---|
| 1 | 标点规范化 | `normalize.py` | 破折号→逗号、分号→句号、全角→半角。**破折号官方明确不支持** |
| 2 | 分句 | `segment.py` | 30 条缩写保护；引号在句号后面（`something." Daniel`）也要能切 |
| 3 | 语义分组 | LLM + 代码校验 | 模型只给句子索引和停顿毫秒；长度/覆盖/停顿数由代码强制 |
| 4 | 逐组合成 | `synth_stream()` | **`language_hints=["en"]` 必传**、`word_timestamp_enabled=True`、`streaming_call` + `streaming_complete` 阻塞等完成 |
| 5 | 拼接 | ffmpeg | 组间插 `gap_after_ms` 静音 |
| 6 | 时间戳对齐 | `align_words()` | 词级时间戳换算成绝对时间 → difflib 对回**原文** token，未命中的插值 |
| 7 | 播放 | `AudioRenderer` | PCM 写入；rAF 按当前时间二分查找高亮；暂停/续播按组偏移 |

**三条实测结论，别再试错：**

1. `language_hints` 不传 → `1990s` 读成「一千九百九十秒」，`2.4` 读成「二点四」。t3 因此慢了 20 秒。
2. 同一文本同参数，输出 md5 完全一致 → 缓存永久有效，重叠合成的裁剪点精确。
3. 时间戳只能取 `sentence-end` 的最终值；`sentence-synthesis` 是增量暂定值，混用会得到 80ms 这种假数据。

**已验证的产物**：`plans/*.json`（语义分组）+ `out/plan/index.html`（高亮对拍页）。三篇：t1 3 组 / t2 3 组 / t3 2 组，全部 ≤300 字符。

### 3.5 语音提问：CQR

任务不是转写，是**指代消解**：把「这个什么意思」解析成「第 12 句第 34–46 字符」。

```
[system] 你是英语课文阅读 App 的提问解析器。用户正在朗读下面的课文，
他会用中文、英文或中英混说提问。判断他问的是哪一句、哪个片段、想了解什么。
规则：只能从给定句子中选择；surface 必须从课文原样复制；输出 JSON；
无法确定时 confidence<0.5；不要转写用户原话，只判断指向。

[课文] 1. ... 2. She remained resilient in the face of failure. ...
[当前播放] 第 2 句
[暂停词] resilient          ← 关键，见下

[输出] {"sentence_id":2,"surface":"resilient","span_start":35,"span_end":44,
        "intent":"meaning","question":"resilient 是什么意思","confidence":0.95}
```

**「暂停词」是必须给的输入，不是可选项。** 实测（10 条纯指示词提问，如「这里什么意思」「这个词呢」）：

| 上下文 | 命中 | 结果 |
|---|---|---|
| 只给「当前第 N 句」 | **0/10** | 每次都返回整句，抓不到具体词 |
| 加「用户在读到 X 时按了暂停」 | **8/10** | 另外 2 条返回 `Mrs. Alvarez` / `had taught`，比预期更准 |

原理很直接：`这里` 是个指代，模型没法从音频里推出它指哪个词；但播放器**知道**暂停在哪个词（时间戳的副产品）。把已有的信息喂进去，不需要模型更聪明。

实现要求：暂停时记录 `{sentence_id, word_index}`，提问请求带上该词。播放位置过期（用户手动拖动过、或距暂停超过 30 秒）就不要带，宁可不给也不要给错。

本地强制校验：句子编号存在 → 优先用模型复制的 `surface` 在原文里定位（拼写永远来自原文）→ 找不到再用 span 截取并吸附到词边界 → 都失败则降级为「当前句 + 让用户点选」。

模型：**Qwen3.8-Omni-Flash**（百炼，OpenAI 兼容端点，`input_audio` 传 data URI，约 ¥0.01/次）。

预期准确率：句中出现原文词 90%+；暂停词 + 指代词 80%+（实测）；纯「这句什么意思」80–90%；长句 + 混说 70–85%。所以 UI 永远显示「你问的是：… [改]」。

**实测（真人录音 20 条，2026-10-20）：19/20 命中。** 覆盖面包括单词、短语、句式、读音、整句翻译、纯指代（「这句什么意思」）、以及中英混说。

唯一失败的是 **c19「最后一句讲什么」**（当前停在第 5 句，应指向第 6 句）——模型选了当前句，没有做序数推理。这说明：

- 序数类指代（「最后一句」「上面那句」）不可靠，不要指望；
- 其他所有类型都在 95% 以上，包括最难的纯指代；
- **确认 UI 不是可选项**——就是为这 5% 准备的。

工程上的三条硬规则（都来自实测）：

1. `pause_word` 必传——不带它，纯指代类问题命中率是 **0/10**；
2. 提示词里要求模型**原样复制** `surface`，下标只做兜底（模型给的 `span_start` 会差一两位）；
3. `surface` 为空且 span 越界时，按**整句**处理，否则「这句什么意思」会返回 `"You'll` 这种碎片。

### 3.6 主 Agent

```
messages = [system, 当前段落, CQR 结果, 最近 6 轮]
loop ≤ 6: r = llm(messages, tools)
          tool_calls → 并行执行 → 回填
          else → 流式输出
```

| 工具 | 实现 |
|---|---|
| `lookup_dictionary(term)` | relationalStore 查 ECDICT → 未命中走有道/腾讯词典 |
| `lookup_phrase` / `search_web` | 博查 Search API / 自建 SearXNG |
| `get_context(sentence_id, n)` | SQLite |
| `append_vocabulary(entry)` | `VocabStore` |
| `play_word(word)` | 调 TTS 点词发音（**Agent 也能主动"读给你听"**） |

**纪律**：释义与音标只能来自工具；`context_sense` 必须引用原句；一次最多写 3 条；查不到标 `[模型释义]`。

### 3.7 存储

```sql
articles(id, title, source_pages, raw_text, created_at, status)
chunks(id, article_id, idx, text, audio_key, duration_ms, subtitles_json)
sentences(id, article_id, chunk_id, idx, text, tts_text, start_ms, end_ms,
          char_start, char_end)
-- 一组一次合成，组内多句共享一个音频文件，句子用 start_ms/end_ms 定位
-- tts_text：朗读稿覆盖（默认等于规范化后的 text），支持单句手工修正
vocab_entries(id, kind, surface, lemma, phonetic, pos, context_sense,
              dict_defs, collocations, examples, article_id, sentence_id, quote, created_at)
threads(id, article_id, created_at)
messages(id, thread_id, role, content, tool_json, created_at)
dict_entries(lemma, phonetic, pos, defs, stars, freq)
```

`vocab.txt` 格式不变（块式 + `---` + UTF-8 BOM + CRLF），导出走 `DocumentViewPicker`。

## 6. UI：MatePad 横屏优先

7. **字体缩放**跟随系统（最大 2×），行高 1.6，正文 18–20fp。

## 7. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 选定音色不支持时间戳 | 只能句级高亮 | 启动校验音色能力；换音色 |

| 英文 OCR 质量未知 | 段落还原差 | 实测；不达标切云 VLM |
| Key 泄露 | 账号被盗刷 | 用户自填 + 加密存储；或走 Token 代理 |
| CQR 解析错 | 答非所问 | 置信度阈值 + 「你问的是…[改]」 |
| 大模型 TTS 读错生词 | 跟读学错 | 点词单独发音（该词单独合成，可控性最高）；SSML 无效 |
| 断网 | 无法朗读新段落 | 缓存兜底；离线包 |
| 调试签名过期 | App 打不开 | 到期重签或走上架 |

## 9. 验证路线

排序不是按「模块重要程度」，而是按 **推翻方案的概率 × 验证成本**。

三条原则：

1. **先验会推翻选型的，再验会推翻架构的，最后做确定能做的工程。** 音色和时间戳不行，整个 App 的体验假设就不成立；Agent 和 UI 无论怎么验都能做出来，放最后。
2. **能在电脑上验的，绝不等到 App 搭好。** TTS 和 CQR 都不依赖鸿蒙——`curl` + 一段 Python 就能出结论，半天的事不要排到两周后。
3. **一次只验一个变量。** 把 TTS 和播放器混在一起测，失败时你分不清是音色差还是播放器有 bug。

### 9.1 批次与门禁

| 批次 | 验证的假设 | 环境 | 通过标准 | 不通过怎么办 | 工时 |
|---|---|---|---|---|---|
| **B0-a** 音色 | 找到能连听一小时的声音 | 电脑脚本 | ✅ **已过**：四个英文音色均可接受 → 改为用户自选（§3.4.0） | — | 0.5d |
| **B0-b** 时间戳 | 字级时间戳能驱动高亮 | 电脑脚本 | ✅ **已过**：三篇 78/79/57 词 100% 对齐；数字读法、断句、组间衔接均已确认 | — | 0.5d |
| **B0-b2** 语义分组 | LLM 能稳定产出合规分组 | 电脑脚本 | ✅ **已过**：DeepSeek 分组与人工判断一致，0 重试 0 回退；t3 触发 1 次代码修长 | — | 0.5d |
| **B0-c** CQR | 音频+课文能解析出句子和片段 | 电脑脚本 | ✅ **已过**：真人录音 20 条命中 **19/20**（阈值 17） | 未过则退到点选+打字 | 0.5d |
| **B1** 工程基线 | 能装、能联网、权限能拿到 | 真机 | 空工程装到平板，相机/麦克风/网络各通一次 | 换签名方式 | 0.5d |
| **B1.5** 工具调用闭环 | ArkTS 能正确解析并回传 `tool_calls` | 真机 / 模拟器 | 定义一个 `echo` 工具，模型调用后正确回传；再用 `append_vocabulary` 真写一条到 `vocab.txt` | 改手写解析 / 换模型 | 0.5d |
| **B2** OCR | Core Vision 认不认英文课本 | 真机 | 5 页中 ≥4 页段落顺序正确，字符准确率 ≥95% | 主路切云 VLM | 0.5d |

| **B4** 稳定性 | 断网/限流/token 过期 | 真机 | 每种异常都有明确提示且能恢复 | 补降级逻辑 | 0.5d |

**总耗时约 4 天**，其中 B0 三件可以一天内跑完。

### 9.2 关键路径

```
B0-a 音色 ──┐
B0-b 时间戳 ─┼──→ B1 基线 ──→ B3 播放器 ──→ M1
B0-c CQR ───┘                      ↑
B2 OCR ────────────────────────────┘（可并行）
```

B0 全过，这个 App 基本就做得成；B0 不过，后面写多少代码都白搭。所以**先花一天把 B0 干掉**。

### 9.3 各批怎么做

**B0（电脑，一天）**

准备同一份素材：三段固定文本——记叙带对话（测语调）、说明长句（测从句节奏）、数字与缩写专名（测 `1990s` / `U.S.` / `$1.2 billion` / `Dr.` 的读法）。朗读内容只有英文，不需要中英混排样本。

- 音色：**先只测 CosyVoice 内部的 4 个英文音色**（成本 <¥1）。都不到 4.0 再补测豆包 / MiniMax，别一上来开三家账号。盲听时文件名必须匿名。
- 时间戳：把 `subtitles` 导出成 SRT，套在原音频上播放，肉眼核对高亮是否跟手；更严谨的做法是按「时间 × 采样率」切 PCM 波形，逐词对齐看偏差。
- CQR：录 20 条你自己的提问（**必须包含 5 条不说主语的「这个什么意思」**），连同课文一起发给 Qwen3-Omni，人工核对 `sentence_id` 和 span。
- 延迟：从发请求到第一块音频返回，记录 P50/P90。

> **工具已就绪**：`validation/B0A/`。`synth.py` 负责取样（含首包延迟采集）、`blind.py` 负责匿名打包与算分、`texts/` 是三段固定文本、`scores.csv` 是评分表。操作步骤见该目录 `README.md`。

**B1（真机，半天）**：空工程 → 装到平板 → 相机、麦克风、网络各调一次 → 确认调试签名有效期。

**B2（真机，半天）**：真实课本拍 5 页（不同光照/角度），逐页记录「字符准确率 / 段落顺序 / 中文注释是否误入 / 双栏是否正确」。

**B3（真机，一天）**：用 B0 缓存好的 3 段 PCM，做一个只有播放条的页面——播放、暂停 10 次、跳句、切倍速、后台 5 分钟、锁屏控件。**这一批不要接 TTS 接口**，用本地音频，把变量隔离掉。

**B4（真机，半天）**：飞行模式、限速、token 过期、并发合成 3 段。

### 9.4 不需要 spike 的部分

Agent 工具链、`vocab.txt` 落盘、横屏三栏布局——这些不存在「能不能做」的问题，只有「做多久」的问题，按里程碑排期即可，不要为了验证它们而推迟 B0。
