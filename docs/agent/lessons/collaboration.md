# 与人类协作 / 项目推进经验

> 来自这个项目的人类反馈，是**这个人**的偏好，不完全通用；但同类协作大多适用。

## 他的偏好（原话归纳）

- **先查文档，别猜**：「以后不清楚问题记得查文档」。为此专门做了 MCP 插件。
- **要证据，不要表态**：喜欢「实测 X 秒 / 0.39 分每篇 / 600 词」这种数字，不喜欢「应该可以」。
- **怕浪费**：反复强调「不要重复合成，省钱」「能用缓存就用缓存」。
- **宁可大改也要对**：「不用怕改动大」——只要方案更简单/更高效。
- **方案要写下来再动手**：UI 决策、待办都要先成文（`docs/UI设计.md`、`docs/待办清单.md`）。
- **每个事项要有备用方案**：他明确要求「各事项还要有备用方案」。
- **发现方向错了会直接纠正**，比如「提问已经决定用大模型，见交接说明」——
  这时候不要辩解，立刻按已定方案改，并把更正写进文档。

## 有效的做法（被证明有用）

| 做法 | 效果 |
|---|---|
| 先写「探针页」再改主流程 | 一次验证一个 API，失败不会污染产品页 |
| 失败时**打印真实数值**而不是猜 | 坐标那次，一行 `d=2.31 e=890,106 w0=130` 直接定位问题 |
| 明确说「我错了 + 正确结论 + 证据」 | 他接受纠正，但要求写进文档防止重犯 |
| 每步给「可复制命令 + 验收标准」 | 他能自己复现，不必依赖我 |
| 大幅简化时主动删旧代码 | 例如删掉 280 行手写 WebSocket，减少维护面 |

## 无效甚至有害的做法

- **凭记忆写 API 签名**：几乎必错（`TextController` 不是 kit 导出、Rect 没有 width）。
- **盲试参数**：坐标问题我盲试了 6 轮，最后靠打印数值+查文档才解决。
- **在对话里承诺但不落盘**：上下文一压缩就没了 → 所有结论写进 `docs/`。
- **过度设计**：曾想自建相机/自研切边，最后系统控件一行搞定。

## 协作节奏（实际有效的）

1. **先对齐目标**（一句话：要做什么、验收是什么）；
2. **查文档**（MCP）→ 若有不确定，写成 3 个以内的方案让他选；
3. **写探针**验证最难的那一环；
4. **接主流程**，一次只改一条链路；
5. **设备验证 + 截图**，报「实测数字」；
6. **落盘**：结论进 `docs/`，进度进 `docs/agent/project/state.md`。

## 交接的教训

- 他会在上下文快满时主动提示「开一个 agent 目录」——**这是正确姿势**，
  因为压缩会丢掉「为什么这么决定」「哪些方案已被否决」。
- 写交接文档时，**「被否决的方案 + 理由」比「已完成的清单」更有价值**：
  已完成的看代码就知道，被否决的只有文档记得。
